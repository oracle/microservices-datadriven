## Complete event loop

Chapter 14 shows the `events,ai,blockchain` path. Coral arrows trace submission through the AI consumer and human review. Rejection saves written corrections on the ticket and publishes a feedback event back to the same TxEventQ topic. Approval keeps the saved summary; it neither publishes another event nor resolves the ticket.

Ticket submission emits `TICKET_SUBMITTED`; rejection emits `TICKET_FEEDBACK_SUBMITTED`. The ticket producer and feedback producer are separate instances, each committing its database changes and event on its own producer connection. The consumer regenerates assistance using the previous assistance and accumulated feedback, then commits the new result, event outcome, and acknowledgement together. External OCI calls are outside that database atomicity guarantee.

Dashed arrows show failure and manual replay. Retryable failures receive bounded retries; nonretryable failures can go directly to a saved failure outcome. The failure record is a database worklist entry, not a queue. Replay preserves the event type and publishes a new UUID linked to the original event. Durable outcomes suppress duplicate delivery, including an original failure already marked `REPLAYED`.

## Schema reading guide

[Start at the schema overview in the gallery](index.html#schema-overview), then follow chapters 10–13. These are selected-column schematics; [init.sql](../../../db/init.sql) remains the complete DDL. All eight tables are created during fresh database bootstrap, with AI assistance and blockchain review available by default. The application prepares the TxEventQ topic separately; its backing objects are not included in the eight application tables.

- **Event outcomes:** arrows in chapter 10 show application associations. Neither event table declares a ticket foreign key, and both permit a missing ticket ID so malformed or nonexistent-ticket events can still have an outcome. Deduplication checks both tables, including failures already marked `REPLAYED`.
- **AI relationships:** arrows in chapter 11 run from parent to child and represent declared foreign keys. `PK` means primary key and `FK` means foreign key. Each ticket has zero or one assistance row and zero or many saved matches. The two match tables use composite primary keys; both marked `PK` fields together identify a row. Only `related_ticket.ticket_id` has a foreign key; `related` stores the other ticket ID without an enforced relationship. Ticket-owned assistance and match rows use cascading deletion.
- **AI startup:** both embedding columns are `VECTOR(1536, FLOAT32)`. `PolicyIndex` creates missing policy and recorded-resolution reference ticket embeddings at AI startup before the event consumer starts. Ticket embeddings, summaries, suggested resolutions, and matches are saved during enrichment. Rejection appends feedback and publishes a regeneration event atomically with the review snapshot. The consumer includes that feedback and the previous assistance, then replaces assistance and matches in its event transaction. The small corpus uses exact cosine search; these diagrams do not imply an approximate nearest-neighbor index.
- **Replay:** the dashed card in chapter 12 is a new queue event, not another table. Its new UUID permits processing while the original failure remains recorded. The original event becomes the new event's `causation_id`; their `correlation_id` stays the same.
- **Approval snapshots:** the dashed arrow in chapter 13 represents copying in application code, not a foreign key to `ticket_assistance`. A review references its ticket and copies the summary and suggested resolution into `reviewed_summary`, plus model and prompt metadata into the history row. `summary_digest` covers the complete reviewed text using SHA-256; the blockchain table separately hashes rows with SHA2-512. Sixteen-day row retention does not automatically delete rows at that age. Zero-day table retention permits deliberate lab cleanup. Approval accepts the saved assistance; rejection resets the ticket to `RECEIVED` and requests regeneration through TxEventQ. Both append history without executing support actions.
